# WeKnora Wiki Build Pipeline Explained

> Status: Reference · Date: 2026-10-13 · Author: rywang
> Based on: `WeKnora/` (Go source, cloned snapshot) · Python port: `llm-wiki/wikibuilder/`

---

## 0. How to read this document

This document explains, at code level, how WeKnora turns uploaded documents into a wiki. It answers:

- What the stages are, and what each one's inputs, outputs, and failure behavior are
- Where every LLM call happens, what its prompt defines, and what its output format is
- **Which parts of a page come from rules and which are generated by the LLM**
- How incremental updates (adding, modifying, deleting documents) keep the wiki consistent

The full prompt text is in `wikibuilder/prompts.py` (extracted verbatim from `internal/agent/prompts_wiki.go`). This document only covers each prompt's **purpose, inputs, rules, and output format**.

Terms:

| Term | Meaning |
|---|---|
| knowledge / document | One uploaded source document; in WeKnora it has a `knowledge_id` |
| chunk | A text fragment produced by the document parser; the smallest unit of citation |
| slug | Unique page identifier, e.g. `entity/acme-corp`, `concept/rag`, `summary/<knowledge-id>` |
| SlugUpdate | "A change one document wants to make to one page"; the intermediate product between map and reduce |
| map / reduce | map: per document, produces SlugUpdates. reduce: per slug, merges all SlugUpdates into the page |

---

## 1. Overall flow

```
Upload document
  └─ docreader parses → chunks (chunk_size 512, overlap 50)
       └─ post-process: queue a wiki:ingest pending op (dedup_key = knowledge_id)
            └─ triggers a batch after a 30s debounce
                                    ┌──────────────────────────────────────────┐
  ProcessWikiIngest (≤5 docs/batch) │ ① MAP (each doc in parallel, ≤10)        │
                                    │    Pass 0  candidate entities/concepts  LLM│
                                    │    Dedup   merge into existing pages LLM*│
                                    │    Summary doc summary page   LLM ┐ par- │
                                    │    Citation chunk citations   LLM ┘ allel│
                                    │    reconcile with old pages (retract)    │
                                    │ ② Identity remap (rule)                  │
                                    │ ③ Taxonomy plan (one per batch)    LLM   │
                                    │ ④ REDUCE (each slug in parallel, ≤10)    │
                                    │    summary page: write directly (rule)   │
                                    │    entity/concept: rewrite page    LLM   │
                                    │ ⑤ publish (draft → published)            │
                                    └──────────────────────────────────────────┘
                                                      │ write finalize rows
  ProcessWikiFinalize (debounced, once per KB)        ▼
      rebuild index introduction                                          LLM
      dead-link cleanup (rule)
      cross-link injection (rule)
```

`*` Dedup only calls the LLM when "similar but not identical" candidates exist.

### LLM calls per document (rough count)

| Stage | Calls |
|---|---|
| Pass 0 candidate extraction | 1 (on failure, +1 fallback extraction) |
| Dedup | 0–1 |
| Summary | 1 |
| Chunk citation | ⌈document chars / 12000⌉ |
| Reduce | 1 per entity/concept page involved (shared across documents in the same batch) |
| Taxonomy | per batch, ⌈new items / 60⌉ |
| Index introduction | 1 per finalize |

## 2. Preparation: parsing, chunking, content reconstruction

The wiki pipeline doesn't parse files itself. It reads the chunks docreader has already produced.

| Item | Behavior | Source |
|---|---|---|
| Chunk splitting | `chunk_size: 512`, `chunk_overlap: 50`, split markers `\n\n`, `\n`, `。` | `config/config.yaml` |
| Content reconstruction | `reconstructContent`: keep only text chunks, sort by order, **remove overlap**, join | `wiki_ingest.go` |
| Image enrichment | `reconstructEnrichedContent`: inline image OCR text and captions back into the content, so scanned documents aren't left with only image links | same |
| Length cap | Truncate to **32768 runes** after reconstruction (`maxContentForWiki`) | same |
| Empty-content guard | After stripping image markup, **< 10 runes** of real text → skip, **no LLM calls** (prevents hallucinating from filenames) | `hasSufficientTextContent` |
| Document title | Use the knowledge `title`; if missing, the first line of the first chunk (< 200 chars, `# ` removed) | `mapOneDocument` |
| Citation source | `sourceRef = knowledge_id` (**deliberately not the filename**, so the filename never leaks into later prompts) | same |

> The full content is used by Pass 0 and Summary. The chunks are used by the citation pass and by reduce (which quotes chunk text verbatim).

## 3. Triggering, queues, and concurrency

### 3.1 Queue model

- Each document becomes one row in `task_pending_ops`: `task_type="wiki:ingest"`, `scope=knowledge_base`, `dedup_key=knowledge_id`. Re-uploading the same document doesn't add a duplicate row.
- After enqueueing, a **debounced trigger is scheduled 30 seconds later** (`wikiIngestDelay`). Multiple triggers within the window collapse into one. The first worker to get the lock processes the batch; later ones see an empty queue and exit.
- Each batch takes **at most 5 rows** (`wikiMaxDocsPerBatch`, adjustable via `WikiConfig.IngestBatchSize`). If rows remain, a follow-up runs 5 seconds later.
- Deletion uses the same queue with `op = retract` (§10).

### 3.2 Concurrency and locks

| Item | Default | Notes |
|---|---|---|
| map parallelism | 10 | `IngestMapParallel` |
| reduce parallelism | 10 | `IngestReduceParallel` |
| citation batch parallelism | 4 | per document |
| concurrent batches per KB | 4 | `IngestMaxInflight`, so one KB can't monopolize the model |
| Per-slug lock | wait 2 min, TTL 5 min | concurrent batches writing the same page are serialized; on timeout, the document is re-queued |
| Identity claim | TTL 2h | Redis key `wiki:identity:<type>:<normalized title>`, so concurrent batches converge the same name onto one slug |

### 3.3 Failure handling

| Situation | Handling |
|---|---|
| Transient LLM errors (408/429/5xx/timeout) | Up to 3 attempts per call, backoff 2s → 4s |
| Summary generation fails | **The whole document fails** and is re-queued (a document without a summary counts as half-done) |
| Pass 0 fails | Fall back to single-shot extraction (§5.2) |
| One citation batch fails | Ignore that batch; other batches continue (affected items fall back to `details`) |
| Reduce for a page fails | That slug is recorded as `additionFailed`; links pointing to it from summary pages are turned into plain text |
| Row guard refuses a write | The LLM rewrite dropped too many table rows → keep the old content, re-queue the document |
| Document fails more than 5 times | Goes to `task_dead_letters` |
| Document deleted while processing | Checked twice (map and reduce); the deleted document's content is discarded |
| Hit rate limit | Next batch is delayed 60s |

## 4. Data model: WikiPage

| Field | Meaning |
|---|---|
| `slug` | Unique within the KB, `<type>/<name>` |
| `title` | Display name |
| `page_type` | `summary` / `entity` / `concept` / `index` (`synthesis` / `comparison` are reserved for agent use and not produced by ingest) |
| `status` | `draft` → `published` (after ingest finishes) / `archived` |
| `content` | Full markdown body |
| `summary` | One-sentence description for the index |
| `aliases` | Aliases (abbreviations, translations, full and short names) |
| `folder_id` / `category_path` | Taxonomy position (at most 2 levels) |
| `source_refs` | Source documents (`knowledge_id`, document level) |
| `chunk_refs` | Chunk IDs cited (empty for summary pages) |
| `out_links` / `in_links` | Outbound / inbound links (parsed from `[[...]]` in the body) |
| `version` | Incremented **only** when user-visible fields change; link maintenance and bookkeeping writes don't count |
| `last_edit_source` | `pipeline` / `agent` / `user` / `revert` |

Links in the body always use the form `[[slug|display name]]` or `[[slug]]`.

## 5. Map stage (per document)

Entry point: `mapOneDocument` (`wiki_ingest_batch.go`).

### 5.1 Pass 0: candidate entity/concept extraction (`WikiCandidateSlugPrompt`)

**Purpose**: List the "skeleton" of every entity and concept worth a page. It deliberately **doesn't write full facts**; those come later from verbatim chunks via the citation pass, so this stays cheap even for long documents.

**Inputs**

| Variable | Content |
|---|---|
| `Content` | Full document (truncated to 32768) |
| `PreviousSlugs` | The entity/concept slugs this document produced last time (for reparse); first time: `(none — this is a new document)` |
| `Granularity` / `GranularityGuidance` | Extraction granularity and its rules (below) |
| `Language` | Output language |
| `CustomInstructions` | KB `extraction_instructions` (scope `wiki_extraction`) |

**Rules the prompt defines**

1. Return JSON `{"entities": [...], "concepts": [...]}`, with all names and descriptions in `Language`.
2. Empty content → return empty arrays; **inventing from other clues is forbidden**.
3. **Slug continuity**: anything in `PreviousSlugs` that still appears must reuse its slug exactly; things that no longer appear must not be output; only genuinely new things get new slugs.
4. **Entity** (people, organizations, products, places, technologies, events…) / **Concept** (topics, methods, theories…) fields:
   - `name`: human-readable name
   - `slug`: `entity/<lowercase-hyphenated>` or `concept/...`; non-Latin names are romanized (pinyin)
   - `aliases`: **only** names for exactly the same thing (abbreviation, full/short name, translation, well-known alternate name). Parent categories, related products, and generic terms are forbidden.
   - `description`: **one sentence, 15–40 words**, used in the index listing, understandable on its own
   - `details`: 1–3 sentences, < 300 chars, **used only as a fallback when citation fails**
5. Something named and specific goes only in entities; something abstract goes only in concepts; never in both.
6. JSON string values must not contain literal newlines.

**Granularity**

| Mode | Includes | Excludes |
|---|---|---|
| `focused` | Only the document's main subjects, **3–7 items total** | Tech stacks mentioned in passing, general methods, background places/schools, anything that only merits one sentence; when in doubt, exclude |
| `standard` (default) | Main subjects + secondary items with a paragraph, multi-point list, or 2–3 sentences of content; named methods when the document explains *how* they're used | Items that only appear in a comma-separated list, one-off mentions, items worth only one sentence |
| `exhaustive` | Every named entity and recognizable concept (including technologies, standards, protocols mentioned once) | Only truly generic terms (server, data) and items that appear only in URLs or citations |

**After output**: `cleanLLMJSON` (strip code fences, escape raw newlines) → parse → dedup (§5.3).

### 5.2 Fallback: single-shot extraction (`WikiKnowledgeExtractPrompt`)

Used when Pass 0 fails or its output can't be parsed. Same rules as Pass 0, but:
- There's no granularity parameter; the threshold is "mentioned at least twice or described in detail"
- `details` is 2–5 sentences of full facts (because there's no citation pass afterwards)
- **The citation pass is skipped**; reduce uses `details` as page material directly

### 5.3 Dedup (`deduplicateExtractedBatch` + `WikiDeduplicationPrompt`)

**Purpose**: Merge newly extracted items into existing pages that describe the same thing, so you don't end up with both `Acme Corp` and `Acme Corporation` pages.

**Steps**

1. **Similarity pre-filter (rule)**: for each new item's `name` and every alias, run pg_trgm `FindSimilarPages` and take the **top 5** similar entity/concept pages. Each item keeps **its own** candidate list (`itemCandidates`).
2. **Exact identity (rule)**: if a candidate's normalized title (lowercased, whitespace removed) matches exactly, merge deterministically without asking the LLM. Same type takes priority; if none, a cross-type match is also reused (because the LLM's entity/concept judgment drifts between ingests).
3. **LLM decides the rest**: each item is rendered as XML **together with only its own candidates**:
   ```xml
   <item slug="entity/acme-corporation" type="entity">
     <name>Acme Corporation</name>
     <candidates>
       <page slug="entity/acme-corp" type="entity"><name>Acme Corp</name><alias>Acme</alias></page>
     </candidates>
   </item>
   ```
   Items with no candidates aren't sent (to save tokens and reduce hallucination risk).
4. **Validation (rule)**: a merge the LLM proposes is only accepted if (a) the target is **in that item's own** candidate list, and (b) the types match.
5. **Identity reservation**: through Redis identity claims, the same name across concurrent batches ends up on one slug.

**Rules the prompt defines**
- A merge requires **all** of: the same real-world thing; names/aliases support a name variant (abbreviation/full name, translation, spelling difference); nothing indicates different identity, version, or scope.
- **Shared aliases or acronyms alone aren't enough** (e.g. two different organizations both abbreviated ARC).
- Lots of counterexamples: competing products, different versions (GPT-4 vs GPT-3.5), parent/child concepts (ML vs neural networks), similar certificates (ID card vs residence permit, driver's license vs vehicle registration).
- Principle: **related ≠ same; when in doubt, don't merge** ("two pages for the same thing is better than merging two different things").
- Output: `{"merges": {"<new slug>": "<existing slug>"}}`.

### 5.4 Summary page (`WikiSummaryPrompt`)

**Purpose**: Write a summary page for the document.

**Inputs**: `Content` (full text), `ExtractedSlugs` (candidate list after dedup, in the format `- [[slug]] = name (Aliases: a, b)`), `Language`, `CustomInstructions` (scope `wiki_content`).

> **Deliberately no filename or title is passed**, to avoid hallucinated summaries based on meaningless filenames (like a scanned PDF named `MX5280.pdf`).

**Rules the prompt defines**
1. The first line must be `SUMMARY: <one sentence, 15–40 words>` (used by the index).
2. Then a complete markdown summary: key facts, arguments, conclusions.
3. Use `##` / `###` heading levels.
4. **Link rule**: whenever a name or alias from the list appears, it **must** be written as `[[slug|display name]]`, not bold or a bare slug; **inventing slugs is forbidden**.
5. Images: relevant `<image>` items may be inserted as `![caption](url)`, with the URL copied exactly as given.
6. **It must end with a `## Key Takeaways` bullet list.**
7. Length 500–1500 words.
8. Empty content → output a fixed "SUMMARY: No textual content was extractable…" and **no guessing**.

**After output**: `splitSummaryLine` splits off the first line → `summary_line` + `summary_body`.
Summary slug = `summary/<slugify(knowledge_id)>` (uses the ID rather than the filename, which is also less error-prone in prompts).

### 5.5 Chunk citation (`WikiChunkCitationPrompt`), run in parallel with Summary

**Purpose**: For each candidate slug, find the chunks that **substantively discuss** it. Reduce can then write pages from **verbatim chunks**, instead of an LLM paraphrase that's likely to drift.

**Batching (rule)**
- Use text chunks only, ordered as in the document.
- Each batch is ≤ **12000 runes**; an oversized single chunk gets its own batch (content is never dropped).
- Each batch gives its chunks short handles `c000, c001…` (instead of UUIDs) and translates them back to real IDs after output; unknown handles are discarded.
- **Prompt order is designed for prefix caching**: rules + output format + `<candidate_slugs>` (the same for every batch of one document) come first, and the per-batch `<chunks>` come last.

**Inputs**: `CandidateSlugs` (one per line: `- slug: x, type: entity, name: "…", aliases="…", description: …`), `ChunksXML` (`<c id="c003" index="7">…</c>`), `Language`.

**Rules the prompt defines**
- "Substantively" = the chunk states at least one concrete fact, attribute, step, date, number, or relationship about the candidate; **passing mentions don't count**.
- Only chunk IDs from this batch may be cited; candidates with no hits are omitted; a chunk can be cited by several candidates.
- **Secondary task**: if the batch reveals an important item not in the candidate list, it can be added under `new_slugs` (with `type/name/slug/aliases/description/details/source_chunks`).
- Output: `{"citations": {"entity/x": ["c001","c003"]}, "new_slugs": [...]}`.

**Merge (rule, `mergeCitationsIntoItems`)**
- Take the union of citations across batches, sorted in document order → `item.SourceChunks`.
- `new_slugs` that already exist are ignored; the same new slug across batches is merged and its chunks unioned.
- Items with no citations are kept, and reduce falls back to `description + details`.

### 5.6 Producing SlugUpdates and reconciling with old pages

Map's output is a list of SlugUpdates:

| type | Count | Carries |
|---|---|---|
| `summary` | 1 | `summary_line`, `summary_body`, doc title |
| `entity` / `concept` | 1 per item | item (name/aliases/description/details/source_chunks), the document's **full summary body** (as context) |
| `retract` | old pages this document **still mentions** (reparse) | this document's **previous** summary body (the old version's contribution) |
| `retractStale` | old pages this document **no longer mentions** | this document's **new** content |

On reparse, the "old pages" are the pages whose `source_refs` include this document. A `retract` combined with an addition for the same slug gives **"remove the old version, add the new version"** replace semantics, rather than piling the new content on top of the old. Summary pages are overwritten whole, so no retract is needed for them.

## 6. Identity remap (rule)

After all map workers finish, `remapSlugUpdatesByIdentity` re-reads the identity claims. Different documents mapped in parallel may romanize the same name into different slugs (e.g. Chinese names in pinyin), and these are collapsed onto one slug. This must happen **before** taxonomy and reduce.

## 7. Taxonomy (`WikiTaxonomyPlanPrompt`), one per batch

**Purpose**: Assign category folders for the whole batch in a **single call**, so pages don't each invent their own folders in parallel (which diverges worst on the very first batch, when there are no existing folders to anchor on).

**Inputs**
- `ExistingTaxonomy`: existing folders as an indented tree. With ≤ 60 folders, all of them are sent. With more, embedding similarity picks the 3 most relevant per item, capped at 150. With no folders: `(none yet — … design a fresh directory)`.
- `Items`: one per line: `- slug: … | title: … | type: … | about: <description, first 120 chars>`
- At most 60 items per call; folders created by earlier calls are **fed forward** as existing folders for later calls.

**Rules the prompt defines**
1. A path is at most **2 levels**, from broad to narrow. It classifies "**what the thing fundamentally is**", not the role it plays in one document.
2. **Reuse existing folders exactly** when they fit (identical characters); creating synonym folders is forbidden.
3. If nothing fits, **create a new broad, durable folder** (e.g. organizations, legal concepts, places); items of the same kind go in the same new folder.
4. An empty path `[]` should be **rare**; "no matching existing folder" is not a reason for an empty path.
5. Items of the same kind sit at the same depth; type names (entity/concept) can't be folder names; labels can't contain `/`.
6. Every item must appear exactly once; labels are in `Language`.

**Output**: `{"assignments": [{"slug": "...", "path": ["People"]}]}` → `CleanWikiCategoryPath` (rule: cap the depth, remove duplicates and type labels).

**Application rule**: **only applied to pages that don't have a folder yet**. Pages already categorized or moved by a user are never changed (manual edits win).

## 8. Reduce stage (per slug)

Entry point: `reduceSlugUpdates`. All SlugUpdates for the same slug (possibly from several documents in the batch) are handled together.

### 8.1 Summary pages: written directly, no LLM

| Field | Value |
|---|---|
| `title` | `<doc title> - Summary` |
| `content` | `summary_body` |
| `summary` | `summary_line` |
| `source_refs` | append this document |
| `chunk_refs` | **cleared** (summary pages don't carry chunk citations) |

### 8.2 Entity/concept pages: LLM rewrite

**Prompt assembly (rule)**

| Block | Source |
|---|---|
| `<shared_source_contexts>` | One `<document><title><context>` per source document (**the full summary body**), deduplicated and sorted, **placed first** so all pages from the same document share a cacheable prefix |
| `<page_metadata>` | slug / title / type / aliases |
| `<existing_page_content>` | Existing content (old `[c003]` citation markers removed; links replaced with handles); new page: `(New page)` |
| `<new_information>` | Per addition: `**name**: description` + **the cited chunks' original text** (falls back to `details` when there are no citations) |
| `<deleted_documents>` | Content of the documents being retracted |
| `<remaining_source_documents>` | Summary bodies of the documents that remain after the retract (to judge which facts are still supported) |
| `<valid_wiki_links>` | The page's existing outbound links, written as `ref-N (title)` |

**Slug handles (rule)**: real slugs (especially UUID-style `summary/<uuid>`) are replaced with `ref-1, ref-2…`. The model only copies short handles, and code translates them back after output. This fixes the problem of LLMs mistyping long slugs into broken links.

**System prompt (`WikiPageModifySystemPrompt`)**: rules shared by every page, kept separate so the prefix stays stable and cacheable:

*Source grounding*
1. Never output chunk IDs (`[c003]`) in the body; remove any legacy ones.
2. Every newly added fact, entity, or number **must be directly supported** by the new chunks.
3. **No hallucination**: no inventing, synthesizing, or inferring. When the new material clearly and directly replaces old content → update the body and add a "Contradictions / Updates" section. When the conflict is ambiguous → **don't overwrite**; only add a "Contradictions / Updates" section describing it.
4. `shared_source_contexts` is only for calibrating scope, attribution, and tone; **it is not evidence**.
5. System rules take priority over business instructions.

*Editing and output*
1. **"You are a COMPILER, not a creative writer"**: stay close to the source wording; you may lightly reorder, deduplicate, and join sentences, but no stylistic rewording, expansion, or invented transitions.
2. **Don't over-structure**: only add section headings the source or existing page already has; prefer a single top-level heading, short paragraphs, and flat lists.
3. No filler phrases ("aims to provide", "designed to", "旨在", "致力於", "具有重要意義"…).
4. Self-reported claims (resumes, product pages, announcements) must stay attributed and scoped; they can't be elevated into industry facts.
5. Keep content that is still valid; preserve the existing structure and style.
6. Only keep links on the allowed list; never link to the page itself.
7. Images may only come from new material, with URLs copied exactly.
8. The first line is `SUMMARY: <15–40 words>`, followed by the markdown.

**User prompt (`WikiPageModifyUserPrompt`)**: blocks are switched on or off by `HasAdditions` / `HasRetractions`:
- "This page is about **{title}** (a {type}); every statement must be directly about it."
- With retractions: remove facts that **only** came from deleted documents and appear neither in remaining sources nor in new material.
- With additions: **CRITICAL CONFLICT CHECK** first: confirm the new material is really about this page. If it's about something different but related (e.g. this page is Hunyuan but the material is Qwen3; ID card vs residence permit), **reject that part**. If genuinely about this page and contradicting old content, prefer the new.
- Keep content that is still valid.
- Links are limited to `<valid_wiki_links>`; the page's own slug can't appear.
- Use `# {title}` as the H1 if there isn't one; no new heading levels.
- Retracted down to nothing with no new material → fixed output `(empty page)` + "*This page's primary source document was removed.*"

**After output (rule)**
- Truncated by the token limit (`finish_reason=length`) → feed the partial output back as an assistant turn and request a continuation with `WikiPageModifyContinuationPrompt`, **up to 3 times**. The continuation must pick up exactly where it stopped, with no repetition or preamble; if already complete, reply `(complete)`. **Still truncated after 3 rounds → reject the whole result** (no half-written pages).
- Translate handles back → split off the SUMMARY line → write `content` / `summary`.
- `aliases`: union; `source_refs`: append; `chunk_refs`: union with the newly cited chunks.
- `title` / `page_type`: **only set when the page is created**, never changed afterwards.
- **Row guard**: if the rewrite drops too many table rows still on the page → refuse the write and keep the old version (unless the update is a retract).

### 8.3 Publishing

Pages written in this batch go `draft → published` **immediately** (without waiting for finalize), so users see a document's pages as soon as they're done.

## 9. Finalize (debounced, KB-wide convergence)

Each batch writes "affected slugs, their new titles, documents added/removed" to the finalize queue. After the debounce they're processed together, so **a large import rebuilds the index only once**.

### 9.1 Index introduction

The index page's `content` is **only the title + 2–3 sentences of introduction**. The directory listing is rendered by the UI from folders and isn't stored in content.

| Situation | Prompt | Input |
|---|---|---|
| First generation | `WikiIndexIntroPrompt` | The 200 most recent summary pages' `<title>` + `<summary>`; if there are more, add "(showing N most recent of M total documents)" |
| Incremental update | `WikiIndexIntroUpdatePrompt` | Existing intro + this round's change description (`<document_added>` / `<document_removed>`, each with title and one-line summary). **The full set of summaries is no longer passed** (too much context at scale) |
| No changes | — | Keep as is (no version bump) |

Prompt rules: one `# ` title line reflecting the knowledge domain + 2–3 sentences; **no directory or links**; incremental updates keep the same tone, mention new topics that significantly change the scope, and remove topics that no longer apply.
Rules: on failure, keep the old intro (first time: a default template); if the output still contains `\n## …`, it's cut off.

### 9.2 Dead-link cleanup (rule)

For affected pages, find outbound links whose target doesn't exist and try to **redirect** them to a live page (`resolveDeadSlug`, in order):

1. The link's display text exactly matches a live page's title → redirect to that page
2. Normalized slugs are equal (lowercase, `-` and `_` removed) → redirect
3. Character-bigram Jaccard of the slugs ≥ **0.8** → redirect to the most similar one

If none match, the link becomes plain text (the display text; if there isn't one, the last segment of the slug). During a batch, summary pages also get an immediate `sanitizeDeadSummaryLinks` pass for pages whose reduce failed.

### 9.3 Cross-link injection (rule, `linkifyContent`)

For each affected page, take the titles of its existing outbound links plus the titles of every page **newly written in this round** (summary pages use the document title) as candidate strings:
- Match longer strings first; **wrap only the first safe occurrence** of each target as `[[slug|text]]`.
- Skip: code blocks, inline code, existing links, markdown links, autolinks, reference definitions.
- English strings require word boundaries; **a single Chinese character is never auto-linked** (it would cut Chinese words apart).
- If the target slug is already linked somewhere on the page, skip it; never link to the page itself.
- These writes don't bump `version`.

## 10. Deleting a document

`cleanupWikiOnKnowledgeDelete`, done in two steps:

1. **Synchronous (rule)**
   - Write a Redis tombstone `wiki:deleted:<kb>:<kid>` (TTL 1h) so in-flight batches skip this document.
   - Remove this document's pending ingest ops from the queue.
   - For every page whose `source_refs` include it: remove the ref and chunk refs; **if no sources remain → delete the page**; otherwise update the metadata.
2. **Asynchronous retract (LLM)**: enqueue a `retract` op carrying the page snapshot (page slugs from before the deletion) and the document's summary line. When it runs, it **unions** the snapshot with a live re-query (`ListPagesBySourceRef`) so nothing is missed. Each page gets a `retract` SlugUpdate → reduce has the LLM remove facts that **only** came from that document (§8.2).
3. A "document removed" description is recorded for finalize to use when updating the index introduction.

## 11. Who decides each part of a page: rules vs LLM

### Entity / concept pages

| Part | Decided by | Details |
|---|---|---|
| `slug` | LLM proposes → rules correct it | Pass 0 output → normalization → dedup (exact match by rule + LLM decision validated by rule) → identity remap |
| `title` | LLM | Pass 0 `name`, **only set at creation** |
| `page_type` | LLM | Pass 0 classification, fixed at creation |
| `aliases` | LLM extracts → rules accumulate | Union across documents |
| `summary` | LLM | First line of the reduce output |
| **Body** | **LLM** | Reduce rewrite; **no fixed layout**, only style rules (H1, no invented headings, flat lists, Contradictions section) |
| Material fed to the body | LLM + rules | The citation LLM picks which chunks; code assembles the verbatim text into the prompt |
| Links in the body | LLM → rules | LLM limited to the allowed list (handles); afterwards code cleans dead links and auto-injects cross-links |
| `category` | LLM → rules | Taxonomy plan, capped at 2 levels, only assigned to uncategorized pages |
| `source_refs` | Rules | Document-level bookkeeping |
| `chunk_refs` | LLM picks → rules store | From the citation pass |
| `version` / timestamps | Rules | |

### Summary pages

| Part | Decided by | Details |
|---|---|---|
| `slug` | Rules | `summary/<knowledge_id>` |
| `title` | Rules | `<doc title> - Summary` |
| `summary` | LLM | The `SUMMARY:` line |
| Body | **LLM** | **Structure required by the prompt**: `##` sections, ending in `## Key Takeaways`, 500–1500 words, links to the document's entities |
| `source_refs` | Rules | Only that one document |

### Index page

| Part | Decided by |
|---|---|
| Title + introduction | LLM |
| Directory listing | Rules (rendered by the UI from folders) |

> **Implication**: the frontmatter or metadata is almost entirely existing data, so changing it is a rendering change. But the **body layout of entity/concept pages is decided freely by the LLM**. Enforcing a fixed layout requires changing reduce from free-form rewriting to section-by-section generation, which is the biggest departure from WeKnora's design.

## 14. Quality checks (`WikiLintService`)

WeKnora has built-in rule-based health checks (no LLM), which line up with D3 in `evaluation-design.md`:

| Check | Condition |
|---|---|
| Orphan page | entity/concept page with no `in_links` |
| Broken link | `out_links` points to a slug that doesn't exist |
| Empty content | body < 50 characters |
| Stale reference | `source_refs` points to a deleted document |
| Missing cross-reference | another page's title appears in the body but isn't linked |

Health score starts at 100: orphans > 50% −25 (> 25% −10); −5 per broken link; whole wiki has no links (> 2 pages) −15; −3 per empty page.
`AutoFix` automatically fixes three kinds of issues: broken links → plain text; empty-content pages → **archived** (not deleted); stale references → removed (if no sources remain, the page is deleted). Orphan pages and missing cross-references are reported only.

# 附錄：中文逐步解說（以測試文件為例）

> 以下用 `raw/nimbus-labs-overview.md` 和 `raw/cirrus-architecture.md` 兩份測試文件的實際執行結果當例子（模型 `gpt-6-luna`，共 20 次 LLM 呼叫、產生 14 頁），對照上面各章節逐步說明。

## A. 先看全貌：一句話版本

WeKnora 做 wiki 的思路是 **map-reduce**：
- **map（逐份文件）**：讀一份文件，列出「這份文件想對哪些頁面做什麼修改」。
- **reduce（逐頁）**：把所有文件對同一頁的修改收集起來，交給 LLM 一次改寫成最終頁面。

中間產物叫 **SlugUpdate**，意思是「某份文件想對某一頁做的一筆修改」。**slug** 是頁面的唯一 ID，像 `entity/cirrus`、`concept/retrieval-augmented-generation`。

測試執行的 20 次 LLM 呼叫，順序如下：

```
extract_candidates ×2   ← 每份文件一次（Pass 0）
classify_citations ×2   ← 每份文件一次（文件短，各只要 1 批）
summary ×2              ← 每份文件一次
taxonomy ×1             ← 整批一次
page_modify ×12         ← 每個 entity/concept 頁一次
index_intro ×1          ← 最後一次
```

## B. 第 0 步：前置處理（對應 §2）

WeKnora 本身不解析檔案，是 docreader 先把文件切成 **chunk**，wiki 流程直接拿來用：
- **切塊**：WeKnora 每塊 512 字、前後重疊 50 字。Python 版改成依 markdown 標題切，每塊約 1000 字。
- **拼回全文**：把 chunk 拼回去，並去掉重疊的部分。
- **長度上限**：超過 32768 字就截斷。
- **空內容防護**：去掉圖片後實際文字少於 10 個字，就直接跳過，**完全不呼叫 LLM**。這是為了防止掃描檔只剩檔名時，LLM 憑檔名亂編。

後面的步驟有兩種輸入：**全文**給「抽取」和「摘要」用，**chunk** 給「引用」和「改寫頁面」用。

## C. 第 1 步：排隊與觸發（對應 §3）

這段是 WeKnora 線上服務才需要的機制，Python 版簡化成「執行一次指令 = 跑一次」：
- 每上傳一份文件，就排進一個佇列。
- 等 **30 秒**再觸發，讓同時上傳的一批文件可以一起處理。
- 每批**最多 5 份**，處理完還有剩就接著跑下一批。
- 各種失敗也有對應處理：LLM 暫時性錯誤重試 3 次；摘要失敗就整份文件重排；失敗超過 5 次就放棄。

## D. 第 2 步：Pass 0：列出候選的 entity 和 concept（對應 §5.1）

**目的**：先列出「哪些東西值得開一頁」，只寫骨架，不寫完整內容。

LLM 會讀全文，回傳每個項目的 `name`、`slug`、`aliases`、`description`（一句話，15–40 字，給 index 用）、`details`（備用的簡短說明）。

Cirrus 那份文件，LLM 實際列出了：

| 類型 | slug | 別名 |
|---|---|---|
| entity | `entity/cirrus` | — |
| entity | `entity/nimbus` | — |
| entity | `entity/cirrus-cloud` | — |
| concept | `concept/hierarchical-navigable-small-world` | HNSW |
| concept | `concept/retrieval-augmented-generation` | RAG |
| concept | `concept/payload-filtering` | Metadata filtering |
| concept | `concept/segment-based-vector-storage-and-compaction` | — |

**prompt 定義的重點規則：**
- **entity 和 concept 的分法**：具體、有名字的東西（人、公司、產品、地點）放 entity；抽象的東西（方法、理論、主題）放 concept。同一個東西不能兩邊都放。
- **別名只能是「完全同一個東西」的另一個名字**：縮寫、翻譯、全名或簡稱都可以；上層分類或相關產品不行。
- **slug 延續**：文件更新後重跑時，還在的東西必須沿用舊 slug，否則頁面會被拆成兩份。
- **抽取粒度** `granularity`：
  - `focused`：只抽主角，3–7 個。
  - `standard`：預設，主角加上有一段以上內容的次要項目。
  - `exhaustive`：所有提到名字的東西都抽。

如果這一步失敗，就退回「單次抽取」（§5.2）：一次把完整事實寫進 `details`，之後跳過引用那一步。

## E. 第 3 步：去重（對應 §5.3）

**目的**：避免同一個東西出現兩頁，例如 `Acme Corp` 和 `Acme Corporation`。

流程分三層：
1. **程式粗篩**：用字串相似度，替每個新項目找最多 5 個「長得像」的既有頁面。
2. **名稱完全一樣就直接合併**：忽略大小寫和空白後完全相同，不問 LLM。
3. **其他交給 LLM 判斷**：每個新項目**只附上它自己的候選頁面**，問「是不是同一個東西」。LLM 回答後，程式會再驗證一次：目標頁面必須在這個項目自己的候選清單裡，而且類型要相同。

prompt 的核心原則是 **「相關 ≠ 相同，不確定就不要合併」**。裡面列了很多反例，例如 GPT-4 vs GPT-3.5、身分證 vs 居住證，都不能合併。

> **實例**：測試結果中 `Nimbus` 和 `Nimbus Labs` 沒有合併。原因是去重只比對**這批開始之前就已經存在**的頁面，而兩份文件在同一批，開始時 wiki 是空的，沒有任何可以比對的對象。

## F. 第 4 步：寫摘要頁（對應 §5.4）

**目的**：替每份文件產生一頁摘要。

LLM 會拿到全文，以及上一步列出的候選清單（例如 `[[entity/cirrus]] = Cirrus`）。prompt 規定：
- 第一行必須是 `SUMMARY: 一句話`，這一行會拿去當 index 上的說明。
- 接著用 `##` 分段寫摘要，**最後一定要有 `## Key Takeaways`**，長度 500–1500 字。
- 提到清單裡的東西時，**必須**寫成連結 `[[entity/cirrus|Cirrus]]`，不能自己發明 slug。
- **故意不給檔名**，避免 LLM 看著像 `MX5280.pdf` 這種檔名去猜內容。

這一步和下一步（chunk 引用）是**平行**執行的。

## G. 第 5 步：chunk 引用（對應 §5.5）

**目的**：替每個候選項目找出「真正在講它」的 chunk，之後改寫頁面時就能**照原文寫**，而不是讓 LLM 憑印象改寫。

Cirrus 文件的實際輸出：

```json
{"citations": {
   "entity/cirrus": ["c000","c001","c002","c003"],
   "entity/nimbus": ["c000"],
   "concept/hierarchical-navigable-small-world": ["c001"],
   "concept/retrieval-augmented-generation": ["c002"],
   "concept/payload-filtering": ["c000","c002"], ...},
 "new_slugs": []}
```

意思是 HNSW 的頁面只會拿到 c001（「Indexing with HNSW」那段）當素材，RAG 頁面只拿到 c002（「Use in RAG pipelines」那段）。

幾個細節：
- **只算「實質討論」**：chunk 至少要講到一個具體事實、數字或關係；順帶提到不算。
- **分批**：chunk 每 12000 字一批。每批的 chunk 用短代號 `c000, c001…` 代替真實 ID，LLM 輸出後再由程式換回去。
- **順便補漏**：如果某批讀到 Pass 0 漏掉的重要項目，可以放進 `new_slugs`。
- **沒被引用的項目**：不會被刪掉，改寫時會改用 Pass 0 寫的 `details` 當素材。

## H. 第 6 步：整理成 SlugUpdate，並和舊頁面對帳（對應 §5.6）

map 階段最後會把結果整理成一筆筆 SlugUpdate：

| 類型 | 意思 |
|---|---|
| `summary` | 這份文件的摘要頁，1 筆 |
| `entity` / `concept` | 每個項目 1 筆，附上它被引用的 chunk，以及整份文件的摘要（當作背景） |
| `retract` | 文件更新後**仍然提到**的舊頁面：先撤掉舊版內容 |
| `retractStale` | 文件更新後**不再提到**的舊頁面：撤掉這份文件貢獻過的內容 |

後兩種只在**文件被修改後重跑**時才會出現。`retract` 搭配同一頁的新增，效果是「舊版換成新版」，而不是在舊內容上面一直往下加。

## I. 第 7 步：名稱對齊（對應 §6）

這一步是規則，不用 LLM。不同文件平行處理時，可能把同一個名字轉成不同的 slug，最常見的是中文名字轉拼音時拼法不同。這一步會把**名稱完全相同**的項目併成同一個 slug。

`Nimbus` 和 `Nimbus Labs` 名稱不同，所以這一步也沒有合併它們。

## J. 第 8 步：分類資料夾（對應 §7）

**目的**：整批**只呼叫一次 LLM**，替所有新頁面決定分類資料夾。如果每頁各自決定，同一類東西很容易被分到不同名字的資料夾。

測試的實際結果：

```
Technology Concepts: HNSW、Payload Filtering、RAG、Segment Storage、Vector Database
Software Products:   Cirrus、Cirrus Cloud
People:              Daniel Ortega、Lin Mei-Hua、Priya Raman
Organizations:       Nimbus、Nimbus Labs
```

prompt 規則：
- 最多 2 層。
- 依「這東西本質上是什麼」分類，不是依它在某份文件裡扮演的角色。
- 有合適的現有資料夾就**照字原樣沿用**，不能自創同義的資料夾。
- 沒有合適的就開一個大類，很少給空分類。
- **只套用在還沒分類的頁面**：已分類的頁面不會被移動，所以使用者手動調整過的位置會被保留。

## K. 第 9 步：改寫頁面（對應 §8，最核心的一步）

這一步依頁面類型分兩種：
- **摘要頁不用 LLM**：直接把第 4 步的結果寫進去，標題是「文件標題 - Summary」。
- **entity 和 concept 頁每頁呼叫一次 LLM**，收集所有文件對這一頁的修改，一次改寫完成。

以 `entity/cirrus` 為例，程式組出的 prompt 約 14000 字，包含這幾個區塊：

| 區塊 | 內容 |
|---|---|
| `<shared_source_contexts>` | 來源文件的摘要，**只當背景，不當證據** |
| `<page_metadata>` | 這頁的 slug、標題、類型、別名 |
| `<existing_page_content>` | 現有內容。新頁面時是 `(New page)` |
| `<new_information>` | **被引用的 chunk 原文**（例如 Cirrus 被引用的 c000–c003） |
| `<deleted_documents>` / `<remaining_source_documents>` | 撤回時才會有 |
| `<valid_wiki_links>` | 允許連結的頁面，用 `ref-1`、`ref-2` 這種短代號表示 |

**system prompt 的規則**（每一頁都一樣）：
- **「你是編譯器，不是作家」**：貼近原文用字，只能輕微重排、去重、合併句子，不能潤飾或擴寫。
- **不能幻覺**：新增的每個事實都必須有 chunk 支持。新舊資料衝突且新資料明確時，就更新內文並加一段「Contradictions / Updates」；衝突不明確時，不覆蓋原內容，只加這段說明。
- **不要過度結構化**：只用原文或現有頁面本來就有的段落標題。
- **禁用空話**：例如「旨在」「致力於」「具有重要意義」。
- **自述內容要保留出處**：履歷或產品頁上的說法，不能寫成業界事實。

**user prompt 的規則：**
- **先做衝突檢查**：確認新資料真的在講這一頁。例如這頁講混元，資料卻在講 Qwen3，就要拒絕那部分。
- **撤回時**：只刪掉「只有被刪的文件才提到」的事實。

**輸出之後：**
- **被截斷就接續**：輸出因為 token 上限被截斷時，請 LLM 從斷掉的地方接著寫，最多 3 次；還是不完整就整頁不採用。
- **還原代號**：把 `ref-N` 換回真實的 slug。
- **標題和類型只在建立時設定**，之後不會再改。

> **實例**：測試產生的 Cirrus 頁中，數字（M=16、0.97 recall@10、12 ms）和程式碼都跟原文一模一樣，段落標題也直接沿用原文的「Storage model」「Indexing with HNSW」。

## L. 第 10 步：收尾（對應 §9）

收尾在所有批次跑完後執行一次：
1. **index 介紹**：用 LLM 寫標題加 2–3 句介紹，測試產生的是「# AI Data Infrastructure ...」。之後新增或刪除文件時，只把「變動了什麼」交給 LLM 更新，不會重寫整段。index 下方的目錄是程式產生的，不經過 LLM。
2. **清理死連結**：死連結就是指向不存在頁面的連結。WeKnora 會先試著導向相似的頁面，找不到才改成純文字。
3. **自動交叉連結**：內文提到其他頁面的標題時，自動加上連結，每個目標只連第一次出現的地方。程式碼區塊、標題列、已經是連結的地方不碰；單一個中文字不連，避免把詞切斷。測試中有 11 頁被加了交叉連結，例如 Cirrus 頁裡的 `[Daniel Ortega](daniel-ortega.md)`。

## M. 第 11 步：刪除文件（對應 §10）

刪除分兩段：
1. **立刻用規則處理**：所有頁面移除這份文件的來源記錄。移除後**沒有任何來源**的頁面直接刪掉，例如那份文件的摘要頁。
2. **之後交給 LLM 撤回**：還有其他來源的頁面，會在下一批交給 LLM 改寫，刪掉「只有這份文件才提到」的事實。

## N. 第 12 步：哪些是規則、哪些是 LLM（對應 §11）

- **規則決定**：頁面的 ID 和身分最後由程式決定（slug 要經過程式修正，來源記錄和版本號全是程式管）。目錄也是程式產生的。
- **LLM 決定**：entity 和 concept 頁的**內文，以及內文的編排方式**，沒有固定模板，只受風格規則約束。
- **例外**：摘要頁的結構是 prompt 規定的，固定以 Key Takeaways 結尾。

因此 frontmatter 這類欄位幾乎都是現成資料，改格式只要改渲染；但若要求 entity/concept 頁有固定版面，就得把改寫頁面那一步從「自由改寫」改成「逐段生成」，這是跟 WeKnora 設計差最多的改動。

## O. LLM 呼叫的共通機制（對應 §12）

所有 LLM 呼叫都經過同一個包裝函式（`generateWithTemplateResult`），行為一致：

| 項目 | 做法 | 為什麼 |
|---|---|---|
| 模板 | 用 Go 的 `text/template`：`{{.Var}}` 填變數，`{{if .Var}}…{{end}}` 決定區塊要不要出現 | 例如改寫頁面時，沒有撤回就整段拿掉 `<deleted_documents>` |
| 訊息結構 | 改寫頁面：分成 system（共同規則）＋ user（這一頁的資料）；其他呼叫都只有一則 user 訊息 | 共同規則放 system 且內容固定，provider 可以快取這段前綴，省錢省時間 |
| 自訂指令 | 知識庫設定的 `extraction_instructions`（抽取用）或 `content_instructions`（寫內容用）會附在 prompt 最後，包成 `<{scope}_business_instructions>` 區塊，並註明「只在不違反系統的格式、引用、安全、事實規則時才套用」 | 讓使用者可以加業務規則，但不能蓋掉防幻覺等核心規則 |
| 參數 | `temperature 0.3`、`max_tokens 32768`、關閉 thinking | 低溫讓輸出穩定、接近原文 |
| 重試 | 最多 3 次，只對暫時性錯誤（408、429、5xx、逾時）重試，間隔 2 秒、4 秒 | 其他 4xx 是請求本身有問題，重試也沒用 |
| 圖片網址 | 送出前把 `![說明](很長的網址)` 的網址換成短代號，收到輸出後再換回來 | LLM 很容易把長網址抄錯一兩個字，圖片就破了 |
| JSON 清理 | 去掉 ```` ```json ```` 這類包裝，把字串裡沒跳脫的換行、tab 補上跳脫，再解析 | LLM 輸出的 JSON 常常有這些小毛病 |
| 重複請求合併 | 完全相同的請求只會真的送一次（singleflight）；改寫頁面時，第一個請求先送出「暖機」共用前綴的快取，其他請求再平行送 | 同一份文件產生的多個頁面共用很長的前綴，先暖機可以讓後面的都命中快取 |

> Python 版保留了模板、訊息結構、自訂指令、重試、圖片遮蔽、JSON 清理；沒有實作 singleflight 和快取暖機。另外為了配合 `gpt-6-luna`，Python 版可以改用 `max_completion_tokens`，並可以不送 temperature（見 `config.yaml` 的 `token_param` 和 `temperature: null`）。額度用完（`insufficient_quota`）的錯誤不會重試。

## P. 可調參數（對應 §13）

WeKnora 每個知識庫可以各自設定 `WikiConfig`：

| 參數 | 預設 | 調了會怎樣 |
|---|---|---|
| `synthesis_model_id` | 知識庫的摘要模型 | 換 wiki 用的 LLM |
| `extraction_granularity` | `standard` | 抽取粒度。`focused` 頁數少、比較乾淨；`exhaustive` 頁數多、像技術名詞表（見 D 節） |
| `extraction_instructions` | 空 | 附加在抽取 prompt（Pass 0、單次抽取）後面的業務規則，例如「產品型號一律視為 entity」 |
| `content_instructions` | 空 | 附加在摘要、改寫頁面、index 介紹 prompt 後面的業務規則，例如「頁面一律用繁體中文」或想要的段落格式 |
| `ingest_batch_size` | 5 | 每批幾份文件。調小（例如 1）時，後面的文件能跟前面已建好的頁面去重，可以解決 `Nimbus` / `Nimbus Labs` 這種同批沒合併的問題，代價是比較慢 |
| `ingest_map_parallel` | 10 | 同時處理幾份文件 |
| `ingest_reduce_parallel` | 10 | 同時改寫幾頁 |
| `ingest_max_inflight` | 4 | 同一個知識庫最多同時跑幾批，避免一個知識庫把模型額度吃光 |
| `max_pages_per_ingest` | — | 每次 ingest 最多產生幾頁 |

> Python 版對應的設定都在 `config.yaml`：`granularity`、`extraction_instructions`、`content_instructions`、`docs_per_batch`、`map_parallel`、`reduce_parallel`，以及 `llm:` 底下的模型設定。

## Q. 品質檢查（對應 §14）

WeKnora 內建一套純規則的健康檢查（`WikiLintService`），不用 LLM，正好對應 `evaluation-design.md` 的 D3（結構與完整性）：

| 檢查 | 判斷條件 | 白話 |
|---|---|---|
| 孤兒頁 | entity/concept 頁沒有任何頁面連過來（`in_links` 為空） | 沒人連得到它，使用者很難找到 |
| 死連結 | `out_links` 指向不存在的 slug | 點下去會 404 |
| 空頁 | 內文少於 50 個字 | 多半是生成失敗 |
| 過期來源 | `source_refs` 指向已刪除的文件 | 內容可能已經沒有依據 |
| 缺少交叉連結 | 內文出現了別頁的標題，卻沒有連過去 | 錯過可以互連的地方 |

**健康分數**從 100 分開始扣：
- 孤兒頁超過 50% 扣 25 分，超過 25% 扣 10 分。
- 每個死連結扣 5 分。
- 整個 wiki 一條連結都沒有（且超過 2 頁）扣 15 分。
- 每個空頁扣 3 分。
- 最低 0 分。

**AutoFix 自動修三種問題**：
- 死連結 → 改成純文字。
- 空頁 → **封存**（不是刪除）。
- 過期來源 → 移除；移除後沒有任何來源的頁面直接刪除。

孤兒頁和缺少交叉連結只回報，不會自動修。

## R. Python 版跟 WeKnora 的差異（對應 §15）

Python 版（`llm-wiki/wikibuilder/`）的流程和 prompt 跟 WeKnora 相同，差在基礎設施和幾個細節：

| 項目 | WeKnora | Python 版 | 影響 |
|---|---|---|---|
| prompt | `prompts_wiki.go` | `prompts.py` | **用程式原封不動抽出來**，可以直接跟上游 diff |
| 切塊 | docreader，512 字、重疊 50 | `chunker.py`，依 markdown 標題切、約 1000 字、不重疊、不切斷程式碼區塊；chunk ID 是 `文件路徑#c0003` | chunk 比較大，引用比較粗；ID 看得懂，方便評估時追來源 |
| 摘要頁 slug | `summary/<knowledge_id>` | `summary/<文件路徑>` | 檔名看得懂 |
| 去重粗篩 | Postgres 的 pg_trgm | 記憶體內的字元 bigram 相似度 | 效果相近 |
| 跨批次名稱對齊 | Redis identity claim | 沒有（單一程序，不需要） | — |
| 名稱對齊 | `remapSlugUpdatesByIdentity` | `pipeline._remap_by_identity`，名稱完全相同才合併 | 同 |
| 分類資料夾 | 資料夾很多時用 embedding 挑相關的 | 全部送進去（最多 150 個） | 資料夾很多時 prompt 會變長 |
| 改寫頁面 | 有 row guard（改寫掉太多表格列就拒絕） | 沒有 row guard | 大表格頁面有被 LLM 刪減的風險 |
| 撤回後沒有來源的頁面 | 保留成「(empty page)」 | **直接刪除** | 不會留下空頁 |
| 死連結清理 | 只處理受影響的頁面，會先做三段式模糊導向 | 掃整個 wiki，但**沒有導向**，一律改成純文字 | 拼錯的連結會變純文字，而不是被修正 |
| 刪除文件 | `cleanupWikiOnKnowledgeDelete` | `pipeline.remove_document` | 同 |
| 儲存與排程 | Postgres、Redis、asynq 佇列 | `.wiki_state/state.json` 加執行緒池；每次執行指令跑一次，用檔案 hash 判斷新增、修改、刪除 | 不需要任何服務 |
| 呈現 | 網頁 UI | `wiki_format.py` 輸出 markdown + frontmatter；目錄由 `render_index()` 產生；連結格式為 `[標題](相對路徑)` | golden 格式改變時只要改這個檔，再跑 `--render-only` |
| LLM 呼叫 | 見 O 節 | `llm.py` | 沒有 singleflight 和快取暖機 |

## T. 補充 Q&A：抽完 entity/concept 之後，slug 存在哪？頁面怎麼產生？

> 問題：LLM 看完每一篇文件、抽出 entity 和 concept 之後呢？這些 slug 存在哪？接下來是針對每一個 slug，用它對應的文件的 chunk 去產生頁面嗎？產生了哪些？

大致是這樣，但有兩點要修正：
- slug 在抽取完當下**還沒有存起來**。
- 每頁用的 chunk 不只來自一份文件，而是**所有提到它的文件**的 chunk 合在一起。

### T.1 抽取完之後，slug 存在哪？

**在 map 和 reduce 之間，slug 只存在記憶體裡，還沒寫進任何檔案或資料庫。**

map 跑完後，程式會把所有 SlugUpdate 依 slug 分組，得到一個字典（Python 版是 `pipeline.py` 裡的 `slug_updates`）。測試執行時的內容大致長這樣：

```
slug_updates = {
  "entity/cirrus": [
      SlugUpdate(來自 C, 引用 chunk C#c0000~c0003),
      SlugUpdate(來自 N, 引用 chunk N#c0001~c0003),
  ],
  "concept/retrieval-augmented-generation": [
      SlugUpdate(來自 C, 引用 C#c0002),
      SlugUpdate(來自 N, 引用 N#c0003),
  ],
  "entity/priya-raman": [ SlugUpdate(來自 N, 引用 N#c0004) ],
  "summary/cirrus-architecture": [ SlugUpdate(摘要內容) ],
  ...
}
```
（C = cirrus-architecture.md，N = nimbus-labs-overview.md）

要等 reduce 把頁面寫出來，slug 才算真正存起來：
- **WeKnora**：存進資料庫的 `wiki_pages` 表，slug 是每頁的唯一鍵。
- **Python 版**：存進 `.wiki_state/state.json` 的 `pages`，以 slug 為 key。

文件和頁面的對應關係**不是存在文件那邊**。文件紀錄只存 hash、標題、摘要；對應關係存在每一頁的 `source_refs`（來源文件）和 `chunk_refs`（引用的 chunk）上。之後要找「某份文件影響了哪些頁」，就是反過來查哪些頁的 `source_refs` 有它。

### T.2 接下來是每個 slug 用對應的 chunk 產生頁面嗎？

**對，每個 slug 呼叫一次 LLM 產生一頁，但用的是所有文件對它的引用，合起來一次寫。**

以 `entity/cirrus` 為例：
- C 文件引用了 4 個 chunk（c0000~c0003），N 文件引用了 3 個（c0001~c0003）。
- reduce 把這 7 個 chunk 的**原文**一起放進 `<new_information>`，加上現有頁面內容（第一次是空的），**只呼叫 1 次 LLM**，就寫出一頁整合兩份文件的 Cirrus。
- 不是每份文件各寫一頁再合併。

測試中每頁實際用到的素材：

| 頁面 | 來源 | 用到的 chunk |
|---|---|---|
| `entity/cirrus` | C + N | C#0–3、N#1–3 |
| `entity/cirrus-cloud` | C + N | C#3、N#1、N#2、N#4 |
| `concept/retrieval-augmented-generation` | C + N | C#2、N#3 |
| `entity/nimbus-labs` | N | N#0–4 |
| `entity/daniel-ortega` | N | N#0、N#1、N#4 |
| `entity/lin-mei-hua` | N | N#0、N#1、N#4 |
| `entity/priya-raman` | N | N#4 |
| `concept/vector-database` | N | N#1、N#2 |
| `entity/nimbus` | C | C#0 |
| `concept/hierarchical-navigable-small-world` | C | C#1 |
| `concept/payload-filtering` | C | C#0、C#2 |
| `concept/segment-based-vector-storage-and-compaction` | C | C#0 |

有一個細節：**某頁只會拿到「自己的抽取清單裡有這個項目」的文件的 chunk。** 例如 Cirrus 文件其實也提到了 Daniel Ortega（他對 payload filtering 的看法），但 Cirrus 文件的 Pass 0 沒有把他列為候選。引用那一步只會替候選項目找 chunk，所以 Daniel Ortega 這頁只用到 N 的內容，那句話沒有被寫進他的頁面。不過收尾的交叉連結還是在 Cirrus 頁裡把他連過去了。

### T.3 總共產生了哪些？

共 14 頁，加上 1 個 index，總共 15 個檔案。它們的產生方式不同：

| 種類 | 數量 | 怎麼產生 | 用不用 chunk |
|---|---|---|---|
| entity 頁 | 7 | reduce 每頁一次 LLM 改寫 | ✅ 用被引用的 chunk 原文 |
| concept 頁 | 5 | 同上 | ✅ 同上 |
| 摘要頁 | 2 | map 階段讀**全文**產生，reduce 直接寫入，不再經過 LLM | ❌ 不用 chunk（`chunk_refs` 是空的） |
| index | 1 | 介紹文字由 LLM 寫；目錄由程式依分類產生 | ❌ |

整個流程串起來是：

```
每份文件 ──Pass 0──► 候選 slug 清單（記憶體）
         ──引用────► 每個 slug 對應哪些 chunk（記憶體）
         ──摘要────► 摘要頁內容（記憶體）
                          │
              依 slug 分組，跨文件合併
                          ▼
每個 slug ──reduce（1 次 LLM，吃所有文件的 chunk 原文）──► 頁面寫入 state.json
                          ▼
              收尾：index、死連結、交叉連結 ──► 渲染成 wiki/*.md
```

## U. 補充 Q&A：最後那個 index 在幹嘛？

`wiki/index.md` 是整個 wiki 的**首頁和目錄**。打開 wiki 時先看這頁，就知道這個 wiki 在講什麼、有哪些頁面、要點哪裡進去。

### U.1 它由三塊組成

以測試產生的 `wiki/index.md` 為例：

```markdown
# AI Data Infrastructure                                    ← ① 介紹（LLM 寫的）
This wiki covers Nimbus Labs' company, products, ...

## Documents                                                ← ② 文件清單（程式產生）
- [Cirrus Architecture Notes - Summary](summary/cirrus-architecture.md) — 一句話摘要
- [Nimbus Labs Company Overview - Summary](summary/nimbus-labs-overview.md) — 一句話摘要

## Directory                                                ← ③ 分類目錄（程式產生）
### Organizations
- [Nimbus](entity/nimbus.md) — 一句話摘要
- [Nimbus Labs](entity/nimbus-labs.md) — ...
### People
- [Daniel Ortega](entity/daniel-ortega.md) — ...
...
### Technology Concepts
- [Hierarchical Navigable Small World](concept/hierarchical-navigable-small-world.md) — ...
```

| 區塊 | 誰產生 | 內容從哪來 |
|---|---|---|
| ① 標題和介紹 | **LLM**，整個流程最後那 1 次呼叫 | 第一次產生時，交給 LLM 所有摘要頁的標題和一句話摘要，請它寫一個標題加 2–3 句介紹。之後新增或刪除文件，只告訴它「新增了什麼、刪掉了什麼」，請它小幅更新 |
| ② Documents | 程式 | 每份來源文件的摘要頁，連結後面附上那頁的一句話摘要（`SUMMARY:` 那一行） |
| ③ Directory | 程式 | 所有 entity 和 concept 頁，依分類資料夾（taxonomy 那一步的結果）分組排好。沒有分類的放在「Uncategorized」 |

所以真正用到 LLM 的只有最上面那段介紹，目錄完全是程式依現有資料排出來的。每一行後面的說明，就是各頁 frontmatter 裡的 `summary`。

### U.2 它的用途

1. **給人看的入口**：不用一頁一頁翻，從這裡就能看到全部頁面和分類，點進去即可。
2. **給 AI agent 看的入口**：這是 WeKnora 特有的用法。WeKnora 有個能讀 wiki 的 agent，它讀 `index` 這頁時，程式會即時組出「介紹 + 每種頁面類型最多 20 筆」的概覽給它（`internal/agent/tools/wiki_tools.go` 的 `renderIndexOverviewForAgent`）。agent 先看概覽，掌握 wiki 大概有什麼，要找細節時再用搜尋工具。
3. **讓每一頁都至少有一個入口**：沒被其他頁面連到的頁面（孤兒頁），至少還能從 index 點進去。

### U.3 WeKnora 和 Python 版的差別

- **WeKnora**：資料庫裡的 index 頁只存那段介紹文字。目錄是網頁 UI 每次開啟時才依資料夾即時產生的，不存在頁面內容裡。原因是知識庫很大時，完整目錄會變成好幾 MB，存起來或塞給 LLM 都不實際。
- **Python 版**：因為輸出的是 markdown 檔案，沒有 UI 可以即時產生目錄，所以 `wiki_format.py` 的 `render_index()` 會把介紹、文件清單、分類目錄一起寫進 `index.md`。頁面很多時這個檔案會變長，到時候可以改成只列分類，或拆成每個分類一頁。

如果 golden wiki 有自己的首頁格式，例如不要 Documents 區塊、或分類要用表格呈現，改 `render_index()` 就可以，不用重跑 LLM（改完執行 `python build_wiki.py --render-only`）。
